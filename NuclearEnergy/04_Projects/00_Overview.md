# Projects

## Overview

Projects are where this curriculum stops being theoretical. A project proves that you can connect plant understanding, control logic, data flow, software, documentation, and operational reasoning into one coherent artifact.

For this field, the strongest projects are not generic apps. They are plant-shaped systems: a cooling-loop model, a pump-monitoring dashboard, a Modbus data bridge, a reactor transient notebook, or a trip-and-alarm demo.

## How To Use the Project Paths

### Beginner
Choose this if you are still building basic calculation, scripting, instrumentation, and dashboard confidence.

### Intermediate
Choose this if you can already build small tools and want plant-like systems with control logic, historian data, and equipment modeling.

### Advanced
Choose this if you want portfolio pieces that look credible to nuclear, power, automation, or industrial-digital teams.

## Quality Bar for Every Project

Every project should include:

- a short design note or README
- assumptions and engineering limits
- setup and run instructions
- screenshots or plots
- validation or manual verification steps
- one section on tradeoffs, limitations, and next steps

### Real-World Implementation

Projects are where the course stops being claims and starts becoming inspectable evidence. In the nuclear context, a good project does not need to simulate an entire plant. It needs to show one narrow engineering problem handled with the right level of technical honesty, plant context, assumptions, and review discipline.

The strongest projects resemble small pieces of utility, vendor, research, or digital-support work.

### Industry Tool Stack

- `Python`, notebooks, and engineering plots
- synthetic plant tags, historian-style datasets, or simulation outputs
- markdown reports, diagrams, and assumptions logs
- `Git` for traceable changes
- optional modeling tools such as `OpenMC`

### Step-by-Step Applied Workflow

1. Pick a project that maps to a real job family: controls, reactor analysis, reliability, plant data, or digital modernization.
2. Keep the scope narrow enough that validation and documentation can be finished properly.
3. Build the technical core first.
4. Add the engineering wrapper: assumptions, limitations, validation, and reviewer-oriented explanation.
5. Publish the project so another engineer can understand what it proves and what it does not.

### AI Integration

AI can be part of a project, but the project still needs:

- input quality control
- conservative interpretation
- explicit statement that the output is advisory unless proved otherwise

AI-only projects without plant context are weak here.

### Case Studies

- `OpenMC` study repositories: useful benchmark for technical depth plus inspectable code.
- historian and reliability demos: useful benchmark for plant-digital relevance.
- outage or maintenance-support notes: useful benchmark for work that looks operational rather than academic.

### Failure Modes & Safety

- scope too large, so validation disappears
- copied theory with no plant-shaped artifact
- no assumptions or limits section
- project claims imply operational authority the project did not earn

### Business & Commercial Layer

Good projects can point toward:

- utility digital roles
- reliability analytics
- controls and automation work
- simulation and engineering-study support
- consulting and vendor modernization services

### Hiring Signal

The hiring bar is not number of projects. It is:

- one or two strong projects
- reproducibility
- technical clarity
- plant relevance
- honest limitations

### Portfolio Projects

- Beginner: `plant-calculation-pack`
  Deliverables: calculators, diagrams, short technical notes, setup instructions.
- Intermediate: `nuclear-digital-support-demo`
  Deliverables: historian-style data, analytics workflow, reviewer note, screenshots or plots.
- Advanced: `specialization-capstone`
  Deliverables: modeling or reliability system, validation evidence, uncertainty log, architecture explanation.

### Future Trends (2026 / 2030 / 2035 / 2045)

- `2026`: inspectable projects remain the fastest way to prove cross-domain value.
- `2030`: more hiring emphasis on digital-support and modernization artifacts.
- `2035`: stronger value in projects that combine modeling, data, and governance.
- `2045`: honest, reproducible engineering artifacts remain durable portfolio currency.

### Interview Questions

1. What makes a nuclear project credible?
   Short answer: plant context, bounded scope, validation, and clear assumptions.
2. Why is narrow scope important?
   Short answer: because unfinished large projects prove less than complete small ones.
3. How should AI appear in a nuclear project?
   Short answer: as an advisory layer with well-defined limits.
4. What is a common project mistake?
   Short answer: claiming plant relevance without plant-shaped evidence.
5. How many strong projects do you need?
   Short answer: a few inspectable projects usually beat many shallow ones.
