# Portfolio Checklist

## Strong UAV Portfolio Signals

- one flagship repo with a clean README
- one architecture diagram
- one reproducible SITL or simulator setup path
- logs, plots, or telemetry screenshots
- one limitations section
- one failure-cases section
- tests or verification instructions
- one upstream issue or contribution

## Best Project Types

- PX4 or ArduPilot integration capstone
- MAVLink telemetry or mission tool
- ROS 2 offboard project
- OpenCV precision-landing demo
- JSBSim analysis project
- NuttX or driver exploration

## Employer Red Flags

- tutorials copied without adaptation
- no setup steps
- no logs or metrics
- no explanation of trade-offs
- no evidence the project actually runs
- no distinction between simulated and real-hardware claims

## How to Talk About Projects in Interviews

- start with the problem
- explain the system architecture
- describe one failure and how you fixed it
- explain one trade-off you made
- be explicit about simulator, autopilot, and tooling boundaries

## Detailed Portfolio Checklist by Tier

### Tier 1: Minimum Viable Portfolio (Beginner)
These items are required for a portfolio to be considered credible for internship and entry-level applications.

- [ ] **Clean README** — one paragraph describing what the project does, who it is for, and what technology it uses; no unexplained jargon
- [ ] **Quickstart section** — copy-paste commands that produce a running demo from a fresh clone on a documented OS version; verified by the author on at least one other machine or in Docker
- [ ] **Version pins** — PX4 version (git tag or commit hash), ROS 2 distribution (Humble/Jazzy), Gazebo version (Classic/Harmonic/Jetty), Python package versions in `requirements.txt`; no undeclared floating dependencies
- [ ] **One working demo artifact** — a log file, a screenshot, or a terminal output sample showing the project actually ran and produced the expected result; "here is what success looks like"
- [ ] **Limitations section** — at least 2 things the project does not handle; be honest about what was not tested; generic limitations ("does not work in all cases") are not acceptable
- [ ] **requirements.txt or package.xml** — all Python or ROS 2 dependencies declared with pinned versions; `pip install -r requirements.txt` works from a fresh virtualenv

### Tier 2: Competitive Portfolio (Intermediate)
Required for competitive applications to junior UAV software engineering roles at commercial companies.

- [ ] **Architecture diagram** — a block diagram showing the major components and communication links; Mermaid, draw.io, or a clean hand-drawn scan; embedded in the README
- [ ] **Metrics report** — at least 3 quantitative metrics (landing error in meters, position tracking RMSE, EKF innovation RMS, mission completion time, etc.) with units, methodology, and baseline for comparison; auto-generated from the log file by a script
- [ ] **Safety assumptions document** (`docs/safety_assumptions.md`) — operational envelope (max wind, max range, GPS requirements); assumed health conditions (battery threshold, EKF health flags required); failsafe activation thresholds; at least 3 tested conditions and 2 untested ones explicitly labeled
- [ ] **Failure modes document** (`docs/failure_modes.md`) — at least 3 failure cases; for each: what triggers it, what the observed behavior is, and whether it was tested or untested; "tested" means you ran the failure injection in SITL and have a log screenshot
- [ ] **CI badge** — GitHub Actions workflow that runs at minimum a build smoke test; green badge visible on the README; passing on the repo's default branch
- [ ] **Before/after comparison** (for behavior-change projects) — two logs showing the same metric under different conditions; comparison plot generated by a script, not by hand

### Tier 3: Advanced Portfolio (Senior-Candidate Level)
Required for mid/senior UAV software engineering applications and Advanced-tier company screens.

- [ ] **Docker image** — a `Dockerfile` in the repo root that builds the entire environment; `docker run` instructions in the README; tested on a machine other than the author's; the standard for "recruiter-runnable" across operating systems
- [ ] **GSN safety argument** (`docs/gsn_argument.md` or diagram) — Goal Structuring Notation sketch with at least 3 nodes (top goal, sub-goals, evidence references to actual log files or test results); at least one undeveloped node with explicit label and note on what evidence would develop it
- [ ] **Failure injection test results** — at least 2 failure injection scenarios run and documented (GPS disabled mid-mission, ArUco marker out of frame during landing approach, node crash during offboard flight, battery below threshold); for each: a log screenshot showing the autopilot's response
- [ ] **Upstream contribution link** — a link to a real GitHub issue investigated, a PR submitted (merged or documented attempt with post-mortem), or a discuss.px4.io thread where you contributed a verified finding
- [ ] **Coordinate frame documentation** (for perception projects) — explicit documentation of the full coordinate frame chain from sensor to setpoint; numerical verification on a known test case
- [ ] **Multi-vehicle tested** (for multi-vehicle projects) — separation monitoring log covering a minimum 15-minute flight with computed minimum separation; at least one failure injection test

## Interview Preparation Checklist

For each project in your portfolio, prepare the following before any interview:

- [ ] **30-second pitch** — what it does, how it was tested, what it demonstrates about your engineering judgment
- [ ] **Architecture explanation** — be able to describe the system architecture without looking at the diagram; explain why each component was chosen
- [ ] **Hardest debugging problem** — one specific bug you hit, how you reproduced it, how you diagnosed it, how you fixed it; be specific (include the actual error, the wrong assumption, and the fix)
- [ ] **One trade-off you made** — a decision where you chose option A over option B; explain both options, why you chose A, and what you gave up
- [ ] **One thing you would do differently** — a technical decision you now know was not optimal; this shows engineering growth, not weakness
- [ ] **What would fail in 5 m/s crosswind** — for any SITL project, be able to state which component would fail first and why
- [ ] **What version of PX4 this works on** — you must know this; do not guess; have a git tag ready

## Red Flags vs Green Flags in Technical Review

| Signal | Red Flag Version | Green Flag Version |
|--------|-----------------|-------------------|
| README | "A cool drone project" | "ArUco-based precision landing achieving 0.35m median error across 50 SITL trials with 4 m/s wind" |
| Results | "It worked!" | ULog screenshot from Flight Review showing EKF innovations within gate throughout flight |
| Limitations | Absent entirely | "GPS denial not tested; behavior under GPS denial is unknown; SITL only, not hardware-validated" |
| Simulation claim | "This works on a real drone" | "Validated in PX4 SITL v1.14.2 with Gazebo Classic; hardware validation not performed" |
| Dependencies | No setup instructions | `requirements.txt` with pinned versions + Quickstart with copy-paste commands |
| Version | Not mentioned | PX4 v1.14.2 (commit `abc1234`), ROS 2 Jazzy, Gazebo Harmonic |
| Testing | "I ran it and it worked" | 50 SITL trials with distribution statistics; failure injection test results documented |
| Upstream | Not mentioned | Link to github.com/PX4/PX4-Autopilot/pull/12345 (merged) or documented attempt |

## Resume Bullet Formula

**Formula**: "Built [specific artifact] using [specific technology] that [specific measurable outcome]; validated in [specific environment] under [specific conditions]."

**Examples:**

✅ Strong: "Built ArUco marker detection and precision landing system using OpenCV and PX4 MAVSDK achieving 0.35 m median landing error across 50 SITL trials with 4 m/s simulated crosswind."

✅ Strong: "Implemented EKF-based GPS-denied position estimation using optical flow and barometer fusion; validated position error < 1 m for 60-second hover in PX4 SITL."

✅ Strong: "Extended PX4 MAVLink telemetry parser (Python, pymavlink) to detect GPS degradation events in real time; deployed in fleet log processing pipeline handling 200 flights/day."

❌ Weak: "Worked on autonomous UAV systems using ROS 2 and PX4."

❌ Weak: "Implemented precision landing for drones."

❌ Weak: "Learned flight control and computer vision."

## Skills Mapping for Job Descriptions

When reading a UAV job description, map requirements to your portfolio:

- "Experience with PX4 or ArduPilot" → SITL mission project, parameter tuning study
- "ROS 2 development" → ROS 2 offboard demo, integration capstone
- "MAVLink protocol knowledge" → telemetry parser, MAVLink ground tool, mission scripting
- "Computer vision / perception" → ArUco precision landing, OpenCV camera calibration
- "State estimation / EKF" → EKF estimation benchmark, log analysis showing EKF innovation interpretation
- "Embedded / firmware" → NuttX driver reading note, PX4 module development
- "Simulation experience" → any SITL project; specifically call out the version and environment
- "Flight log analysis" → any project with pyulog extraction and metrics; Flight Review screenshots
- "Safety / reliability" → safety assumptions document, failure injection tests, GSN argument
- "Upstream contribution" → link to merged PR or documented attempt on PX4/ArduPilot/MAVSDK
