# Design Thinking

## Overview

Design thinking is a human-centered approach to innovation that starts with understanding the people you are designing for. It follows five phases: empathize, define, ideate, prototype, and test. The method encourages rapid experimentation and treats failure as a learning tool rather than a setback.

---

## Why It Matters

Products built without understanding the user often solve the wrong problem. Design thinking forces teams to spend time with real customers before writing a single line of code or building a single prototype. Companies that adopt it report higher customer satisfaction, shorter development cycles, and fewer expensive late-stage redesigns.

## Key Principles

- Empathy comes first; observe and listen before proposing solutions
- Define the problem as a human need, not a technical specification
- Generate many ideas before committing to one direction
- Build quick, low-cost prototypes to make abstract ideas tangible
- Test with real users early and often; let their feedback guide the next iteration

## Key Terms

| Term | Definition |
|------|------------|
| **Empathy Map** | A visual tool that captures what a user says, thinks, feels, and does to build a deeper understanding of their experience |
| **Point of View Statement** | A concise framing of the user's need that guides ideation, written as "User X needs Y because Z" |
| **Ideation** | The phase where teams generate a wide range of creative solutions without filtering |
| **Prototype** | A rough, fast, and cheap representation of an idea used to gather feedback before full development |

## Use Case

A hospital wants to reduce patient wait times in its emergency department. Instead of hiring consultants to redesign workflows on paper, the administration sends a design-thinking team to shadow patients and staff for a week. The team discovers that the real bottleneck is not staffing but a confusing triage form that forces nurses to ask the same questions twice.

## Scenario

> A bank noticed that small-business owners rarely used its mobile app. A design-thinking team spent three days visiting shop owners and watching them manage finances. They found that owners needed a single screen showing cash in, cash out, and upcoming bills. The redesigned app increased small-business logins by 60% within two months.

## Examples

- IDEO redesigned the shopping cart by observing real shoppers in grocery stores, resulting in a modular cart that was easier to steer and harder to steal
- IBM trained over 100,000 employees in design thinking and reported a 300% return on investment from faster product development and fewer feature rewrites

## 1. Topic Snapshot
Design thinking is a human-centered innovation method that starts with observation and ends with tested prototypes.
For an IT, AI, Product, or Consulting leader, it is the fastest way to avoid building the wrong thing for the wrong user.
The decision it supports is whether the team truly understands the user pain, has framed the problem correctly, and can prove the solution with a quick prototype.

## 3. Frameworks & Matrices

### Design Thinking Loop
**Purpose:** Follow the standard sequence from user understanding to tested solution.

**Text Diagram:**
```text
Empathize -> Define -> Ideate -> Prototype -> Test
```

Axes / Quadrants / Components explained:
Component 1: empathize, which surfaces real user behavior and pain.
Component 2: define, which turns observations into a clear problem statement.
Component 3: ideate, which creates multiple solution options.
Component 4: prototype and test, which turn ideas into evidence.

IT/AI/Product/Consulting worked example: A banking app team interviews small-business owners, discovers that dashboard clutter is the real problem, sketches a simpler cash-flow screen, and tests it with five users before building the full feature.
When to pull this out in a meeting: When the team is debating features but has not yet validated the actual user pain.

### Empathy-to-Prototype Ladder
**Purpose:** Prevent teams from overbuilding before they understand users.

**Text Diagram:**
```text
Observe -> synthesize -> frame -> sketch -> test
```

Axes / Quadrants / Components explained:
Component 1: observe, which captures the user context.
Component 2: synthesize, which turns observations into patterns.
Component 3: frame, which creates a POV statement.
Component 4: sketch and test, which prove the idea cheaply.

IT/AI/Product/Consulting worked example: A SaaS team watches onboarding sessions, realizes the problem is not feature absence but confusion, and tests a guided setup flow instead of adding more tooltips.
When to pull this out in a meeting: When a team wants to jump straight from interviews to coding.

### Prototype-Test Matrix
**Purpose:** Match prototype fidelity to the question being answered.

**Text Diagram:**
```text
Low fidelity / high speed  -> learn structure and direction
High fidelity / slower     -> learn usability and trust
```

Axes / Quadrants / Components explained:
Component 1: fidelity, which ranges from sketches to working builds.
Component 2: speed, which determines how fast learning starts.
Component 3: evidence quality, which improves as prototypes become more realistic.

IT/AI/Product/Consulting worked example: A product team uses paper sketches to test information architecture, then a clickable mockup to test task flow, and only later a coded prototype to test behavior at near-final fidelity.
When to pull this out in a meeting: When the wrong prototype is being built for the question at hand.

## 4. Formulas

Formula: Insight density = validated insights / research sessions
Variables:
validated insights = themes or findings confirmed by multiple users
research sessions = interviews, observations, or tests completed
Why this formula exists: It tells the team whether research is producing actionable learning.
How to interpret the output:
Low value -> weak learning -> improve interview quality
Moderate value -> usable -> keep iterating
High value -> strong signal -> proceed to framing
Worked example with numbers: 8 validated insights from 4 sessions = 2.0 insight density.

Formula: Task success rate = completed tasks / total tasks
Variables:
completed tasks = tasks the user finished successfully
total tasks = tasks attempted in the test
Why this formula exists: It measures whether the prototype actually works for the user.
How to interpret the output:
Low rate -> confusing design -> simplify
Moderate rate -> partial fit -> refine labels and flow
High rate -> strong usability -> scale testing
Worked example with numbers: 18 completed tasks out of 20 = 90% task success rate.

Formula: Learning rate per prototype = validated assumptions / prototype cycle
Variables:
validated assumptions = assumptions confirmed or falsified
prototype cycle = one round of build-test-learn
Why this formula exists: It rewards evidence created per unit of effort.
How to interpret the output:
Low rate -> too much polishing -> cut scope
High rate -> fast learning -> keep the pace
Worked example with numbers: One week of work validates 5 assumptions. The team is learning quickly enough to keep iterating.

## 5. Do vs Don't
| ❌ Don't | ✅ Do |
|---------|-------|
| Start with a solution and hunt for a problem | Start with user empathy and problem framing |
| Treat brainstorming as the whole process | Move from ideation to prototype and test |
| Build a polished product before learning anything | Use low-fidelity prototypes first |
| Assume your internal view matches the user's | Observe real users in context |
| Stop after one round of feedback | Iterate until the evidence is strong |

## 6. Real-Life Scenarios (Metric-Driven)
Scenario 1: Emergency-room intake redesign
Situation: A hospital wants to reduce triage delays, but staff think the problem is understaffing.
Applicable framework/metric: Design Thinking Loop and task success rate.
Analysis: Observation shows the bottleneck is actually a confusing intake form. A low-fidelity prototype of a simplified form can be tested with staff before any major process change.
Decision rule: "If the user flow is unclear, improve the flow before increasing resources."
Action: Reframe the issue, prototype the form, and compare task success rates.

Scenario 2: Small-business banking app
Situation: A bank sees low usage among small-business owners.
Applicable framework/metric: Empathy-to-Prototype Ladder and insight density.
Analysis: Interviews reveal owners want a single cash view, not a complex dashboard. The team should prioritize this need and test a simplified screen quickly.
Decision rule: "If the insight density is high, move to prototype immediately."
Action: Build a one-screen cash-flow prototype and test it with a few target users.

Scenario 3: SaaS onboarding redesign
Situation: A SaaS product has strong signups but weak activation.
Applicable framework/metric: Prototype-Test Matrix and learning rate per prototype.
Analysis: The team suspects onboarding confusion, so it tests a guided setup flow with a clickable mockup before coding.
Decision rule: "If the question is about flow, test it with a low-fidelity prototype first."
Action: Iterate on labels, steps, and guidance until task success rises.

## 7. Implementation Playbook
1. Spend time with users before defining the solution.
2. Convert observations into a single clear problem statement.
3. Generate multiple ideas before narrowing.
4. Match prototype fidelity to the question you are trying to answer.
5. Test with real users early and capture repeatable learning.
6. Iterate on the design based on observed behavior, not internal preference.
7. Keep a research log so the team does not relearn the same lesson.
